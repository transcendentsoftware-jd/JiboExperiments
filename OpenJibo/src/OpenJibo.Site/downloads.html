For Linux tinkerers · Experimental preview

Let’s get a test
server running.

Try OpenJibo on your computer, without changing your robot. We’ll check your setup, verify the download, and start a separate test server.

A preview, not a robot installer. This guide is for a fresh native Linux x86_64 setup. Not a stable release, and not an update to an existing installation. If you’re looking for help with a physical Jibo, start with the revival community.

Your next steps
  1. Check your computer
  2. Prepare the preview
  3. Start your server
  4. Check that it works
Something not working?

Keep the same terminal window open as you work through the steps. Stop if a check fails—don’t skip ahead.

1

Check your computer.

For this preview, you’ll need a Linux computer and a few tools already installed. Windows and Mac instructions aren’t ready yet.

  • Native Linux, x86_64. This guide was tested on Ubuntu. Use the computer where Docker will actually run, not a remote Docker server.
  • Docker and Compose 2.24.4 or newer. Docker must be running and your account must be able to use it.
  • Git, Python 3, Bash, and OpenSSL. These fetch and check the files.
  • A recent GitHub CLI (gh). It must support gh attestation verify, which checks who published the download.

Open a Bash terminal and run this check. It won’t install anything or start a server. GitHub may ask you to sign in when verifying a release; no OpenJibo Cloud account is needed.

Check tools · Linux terminal
(
set -euo pipefail
uname -m
git --version
python3 --version
openssl version
docker info >/dev/null
docker compose version
gh attestation verify --help >/dev/null
echo "Tool checks completed."
)

Look for: x86_64, your tool versions, and Tool checks completed. Check that Compose is at least 2.24.4. These are basic checks; the helper also checks GitHub CLI’s full verification capabilities in step 2. A missing command or a permission error means you should stop and fix that first.

Get the project tools on this computer

The commands below use a trusted, updated checkout at ~/JiboExperiments. Downloading a ZIP alone does not run the guided installer.

First time? If that folder does not already exist, clone the project:

First checkout only
(
set -euo pipefail
test ! -e "$HOME/JiboExperiments"
git clone https://github.com/transcendentsoftware-jd/JiboExperiments.git \
  "$HOME/JiboExperiments"
)

Already have a checkout? Open that trusted repository and run git pull --ff-only. Don’t overwrite an existing folder. If your checkout is elsewhere, use its path instead of $HOME/JiboExperiments below. Inspect the preparer, verifier, and launcher before running them.

2

Prepare the preview.

Start with portable, our default build. The helper downloads the exact release and checks its signed provenance—the evidence that the files came from the expected publisher.

This creates a new, timestamped folder so an older test is left alone, and creates Downloads if needed. Keep this terminal open: the next step uses the same folder and project name.

Verify and prepare · No server starts yet
preview_project="openjibo-preview-$(date -u +%Y%m%d%H%M%S)"
preview_dir="$HOME/Downloads/$preview_project"
(
set -euo pipefail
cd "$HOME/JiboExperiments"
mkdir -p "$HOME/Downloads"
gh attestation verify --help >/dev/null
python3 -B OpenJibo/scripts/cloud/prepare-published-starter.py \
  --channel preview --version runtime-preview-38165346370 \
  --destination "$preview_dir" --plan
python3 -B OpenJibo/scripts/cloud/prepare-published-starter.py \
  --channel preview --version runtime-preview-38165346370 \
  --destination "$preview_dir"
)

Look for: "provenance_verified": true and "docker_started": false. Read the downloaded README before continuing. The --plan output alone does not verify the download.

3

Start your server.

We’ll first check the folder, Docker access, and port. Then the --start command creates the test stack and its private settings. Your computer may ask for your Linux password through sudo.

This example uses the loopback port 8093, reachable only from this computer. If it’s already in use, stop and choose another unused port in both commands.

Check, then launch · Same terminal window
(
set -euo pipefail
: "${preview_dir:?Run step 2 in this terminal first}"
: "${preview_project:?Run step 2 in this terminal first}"
cd "$HOME/JiboExperiments"
sudo -v
python3 -B OpenJibo/scripts/cloud/launch-published-starter.py \
  --directory "$preview_dir" \
  --project "$preview_project" --port 8093 --sudo-docker
python3 -B OpenJibo/scripts/cloud/launch-published-starter.py \
  --directory "$preview_dir" \
  --project "$preview_project" --port 8093 --sudo-docker --start
)

Look for: "docker_started": true and "health_passed": true. The first command is a check only; the second starts the stack. Don’t share the generated .env file—it contains private settings.

4

Check that it works.

Open http://localhost:8093/health in a browser on the Linux computer. You should see a small JSON response containing "ok": true. Optionally, if you have a recent curl with --fail-with-body support, check in the terminal instead:

Check the running server
curl --fail-with-body --max-time 15 http://localhost:8093/health

That’s your first checkpoint—not a connected robot yet. Next, follow the connection and recorded-audio tests, using port 8093 and test robot IDs. These simulate the server side without changing a physical Jibo.

Keep the downloaded folder, private settings, keys, and volumes. There’s no automatic upgrade. Changes to an existing installation need backups and a separate, operator-reviewed update plan.

No need to guess

If something doesn’t work.

“Unknown command: attestation”

Your GitHub CLI is too old, even if your package manager says it is current. Update from the official GitHub CLI instructions, then repeat step 1. Never bypass signature verification.

Docker says “permission denied”

Docker may be running, but your user may not have access to it. Follow your Docker installation’s Linux access instructions, then open a new terminal and recheck. Docker access is powerful; don’t make the socket writable by everyone.

The folder or project already exists

Keep it—especially its private settings and data. Step 2 chooses fresh names for a new attempt. Don’t delete an old directory, keys, or Docker volumes just to make a check pass.

The port is busy, or the page won’t open

Run the launch check before starting. Choose an unused port consistently, and open the browser on the same Linux computer. If startup failed, inspect that failure first; don’t keep creating more stacks.

You’re still stuck

Ask the revival community or report a tooling issue. Include the failed step, software versions, and the error text. Remove secrets and personal information before posting.

For a closer look

Release details & next steps.

Advanced: use the AVX2 build

Use only when Docker runs on this same native Linux host and all CPU prerequisites pass. Do not reuse the portable directory. Prepare with --cpu-profile avx2; launch with --avx2-local-daemon, which confirms locality but does not select a profile automatically.

(
set -euo pipefail
cd "$HOME/JiboExperiments"
gh attestation verify --help >/dev/null
python3 -B OpenJibo/scripts/cloud/prepare-published-starter.py \
  --channel preview --version runtime-preview-38165346370 --cpu-profile avx2 \
  --destination "$HOME/Downloads/openjibo-guarded-avx2-site-test"
sudo -v
python3 -B OpenJibo/scripts/cloud/launch-published-starter.py \
  --directory "$HOME/Downloads/openjibo-guarded-avx2-site-test" \
  --project openjibo-guarded-avx2-site-test --port 8094 --sudo-docker \
  --avx2-local-daemon
python3 -B OpenJibo/scripts/cloud/launch-published-starter.py \
  --directory "$HOME/Downloads/openjibo-guarded-avx2-site-test" \
  --project openjibo-guarded-avx2-site-test --port 8094 --sudo-docker \
  --avx2-local-daemon --start
)

Use port 8094 for follow-up probes. Choose portable when host compatibility is unknown.

What we’ve tested—and what is still open

License/notice review and physical-robot acceptance remain open. Signed provenance is not clearance or stable readiness: it verifies publication, not every dependency’s licensing or every robot’s behavior.

Both current profiles passed fresh native Ubuntu preparation, authenticated socket and recorded-audio probes, database persistence with API stopped, and separate restores of both databases plus API data using the preserved private environment. Restored file contents were checked before API startup; restored probes passed too. These are synthetic laptop results, not physical microphone/playback, sustained capacity, proactive transaction, existing-token survival or encrypted-data decryption certification.

Windows published-bundle acceptance, complete notices/license review, upgrade/rollback and stable channel protections remain outstanding. Signed SPDX verification does not establish dependency completeness or legal clearance.

Exact-image acceptance and recovery evidence

Stopping, updates, and the installer roadmap

Full installer still planned: download, inspect, run; stable by default once a stable release exists, explicit preview opt-in, and targeted version selection. Each selection resolves to verified immutable artifacts. Portable is the default; AVX2 needs an explicit capability check. No latest/stable selector or automatic upgrade is available today.

Updates will be separate, operator-reviewed operations with backups, migration compatibility and recovery checks. Stop this test with the same project and Compose files followed by stop; preserve files, keys and volumes. Do not remove volumes containing data you want to keep.
