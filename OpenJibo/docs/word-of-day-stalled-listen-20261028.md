The repeated immediate right-word listens are an internal inefficiency: the SDK restarts a no-input listener while the optional-response timeout has not elapsed. The observed eight turns over 2.735 seconds finished within the configured three-second window. The log does not expose `ListenResult.state` or `firstGrammarTag`, so the exact state classification is inferred from the SDK behavior, not directly logged. Preserved robot evidence: `artifact-output/voice-investigation-20261027/proscenium-messages.log`.

Follow-up analysis: the cloud's right-word setup responds immediately with local no-input, while the SDK's optional-response listener explicitly restarts early no-input results until its original timeout expires. A bounded production query for the observed four-second window found eight listen replies, eight ignored-audio events, and no STT strategy selections for this session. This does not quantify CPU cost, billing, or fleet-wide frequency. A future optimization would need a cancellable, transaction-scoped deadline that honors the robot's remaining timeout and real speech while avoiding shared audio-finalizer races. No speculative timing change was made for this single successfully completed replay.
